Configure ingestion

The knowledge ingestion settings determine how documents are processed when you upload documents into your knowledge base. This includes chunking strategies, embedding models, and image handling settings.

Existing documents aren't reprocessed after changing ingestion settings​

warning

Changes to knowledge ingestion settings only apply to documents that you upload after making changes. Documents uploaded before changing these settings aren't reprocessed.

After changing knowledge ingestion settings, you must determine if you need to reupload any documents to be consistent with the new settings.

It isn't always necessary to reupload documents after changing knowledge ingestion settings. For example, it is typical to upload some documents with OCR enabled and others without OCR enabled.

Select a Docling implementation​

OpenRAG uses Docling for document ingestion. Docling processes files, splits them into chunks, and stores them as separate, structured documents in your OpenSearch knowledge base.

You can configure OpenRAG to use either a Docling Serve service or a Docling processor pipeline for document processing:

  • Docling Serve ingestion: By default, OpenRAG uses Docling Serve. When you start OpenRAG, a local docling serve process starts, and then OpenRAG runs Docling ingestion through the Docling Serve API.

    To use a remote docling serve instance or your own local instance, set DOCLING_SERVE_URL=http://HOST_IP:5001 in your OpenRAG .env file. The service must run on port 5001.

    For terminal-managed deployments, the OpenRAG terminal session can alert you if docling serve isn't running or isn't detected by OpenRAG. You can also use the terminal's Show status option to inspect and manage the OpenRAG services.

  • Docling processor ingestion: Instead of using a separate Docling Serve service and the Docling Serve API, you can use the Docling processor directly. To do this, set DISABLE_INGEST_WITH_LANGFLOW=true in your OpenRAG .env file, and then restart the OpenRAG services. For the underlying functionality for this option, see processors.py in the OpenRAG repository.

Set the embedding model and dimensions​

When you install OpenRAG, you select at least one embedding model during the application onboarding process. OpenRAG automatically detects and configures the appropriate vector dimensions for your selected embedding model, ensuring optimal search performance and compatibility.

After onboarding, you can change the embedding model on the OpenRAG Settings page. OpenRAG automatically updates all relevant OpenRAG flows to use the selected embedding model and dimensions when ingesting documents.

You can only select models that are available from your configured model providers, such as an Ollama instance or an OpenAI account. For more information, see Troubleshoot model availability and performance issues.

Because the OpenRAG UI validates model availability and compatibility, setting models directly in the OpenRAG .env file isn't recommended.

Documents aren't reingested after changing the embedding model​

OpenRAG doesn't reprocess existing documents when you change, add, or remove embedding models.

If you want to generate new embeddings for existing documents, you must reupload the documents after enabling the new embedding model.

To remove previously generated embeddings, you must remove the existing documents from the knowledge base.

Best practices for multiple embedding models​

  • Make sure the active embedding model is correct before ingesting documents: For ingestion, OpenRAG allows only one active embedding model at a time. The active model is set on the Settings page.

  • Chat searches take longer with multiple embedding models: OpenRAG Chat can use multiple embedding models, regardless of the active model for ingestion. If your OpenRAG knowledge base has documents with embeddings from different embedding models, the agent runs a separate similarity search against each model's embeddings, and then prepares a unified set of search results. Be aware that this can increase processing time for chat responses.

  • Use filters to exclude unrelated models: You can create filters to separate documents that were embedded with different models. For example, if you use a specific model for financial reports, and a different model for corporate policy documents, you can use a filter to exclude the financial reports when chatting about corporate policies. This can save time and improve the relevance of search results because the agent doesn't need to search both sets of embeddings and then unify them into one set of results.

  • Unavailable embedding models can cause errors: Errors can occur in Chat if you an embedding model is unavailable and your knowledge base contains documents with embeddings generated by that model. Similarly, errors can occur with ingestion if the active embedding model (on the Settings page) is unavailable.

Models become unavailable when you remove an embedding model or provider from the OpenRAG Settings page, your model provider credentials are expired or invalid, or there are network issues preventing access to the model.

If you remove a model or provider that you don't want to use anymore, it is recommended that you remove documents that were embedded with the unavailable model. If you don't remove or filters these documents, then Chat responses can fail or return incomplete results. This is because the agent cannot access the model to generate a query embedding for comparison with the document embeddings.

Set the chunking strategy​

Fork-specific feature

The Chunking strategy selector and its Hybrid default are implemented by this fork. They are not presented as official upstream OpenRAG settings.

In Settings > Langflow, under Knowledge Ingest, choose one chunking strategy for new documents:

  • Character uses fixed-size chunks. Chunk size and Chunk overlap are active only for this strategy.

  • Hybrid uses Docling document structure to create semantically coherent chunks. Its active settings are Hybrid max tokens and Merge peers. Hybrid is explicit and fail-fast: if Docling's HybridChunker is unavailable, ingestion fails rather than silently falling back to Character.

Hybrid is the default for new installations and workspaces. Character chunking remains available only as an explicit compatibility choice. Changing the strategy affects new or reingested documents; it does not rewrite existing indexed generations automatically.

Hybrid chunking is not the same as Hybrid retrieval, which means searching both lexical and semantic/vector lanes in Settings > Retrieval.

You can edit the following Character settings on the OpenRAG Settings page in the Knowledge Ingest section:

  • Chunk size: Set the average number of characters for each text chunk when breaking down a file.

    Larger chunks yield more context per chunk, but can include irrelevant information. Smaller chunks yield more precise semantic search, but can lack context.

    The default value is 1000 characters, which is usually a good balance between context and precision.

    warning

    The Chunk size must be less than the maximum token length supported by your embedding model. To determine this value, see the documentation for your embedding model or provider.

    Because Chunk size is an average, actual chunks can be larger or smaller than the specified value. To account for variations in chunking and ensure that no chunks exceed the model's limits, Chunk size must not be equal to the model's maximum token length.

    If ingestion fails with errors like ContextLengthExceeded and reduce the length of the input, this indicates that some chunks exceed the model's maximum token length. Decrease the Chunk size, and then retry ingestion. Repeat this process until you find a value that works consistently for your documents and embedding model.

  • Chunk overlap: Set the number of characters to overlap over chunk boundaries.

    Use larger overlap values for documents where context is most important. Use smaller overlap values for simpler documents or when optimization is most important.

    The default value is 200 characters, which represents an overlap of 20 percent with the default Chunk size of 1000. This is suitable for general use. For faster processing, decrease the overlap to approximately 10 percent. For more complex documents where you need to preserve context across chunks, increase it to approximately 40 percent.

All ingestion settings that affect the document representation — embedding provider/model, chunking, Docling extraction, OCR, tables, and picture descriptions — apply only to future ingestion. OpenRAG does not automatically rebuild or remove existing indexed documents after a change.

Large documents are indexed through bounded OpenSearch bulk requests (at most 64 chunks and approximately 5 MiB per request). This is an ingestion safety contract, not a document-size limit: every verified leaf chunk is still written, then the complete generation is profiled and promoted atomically. Splitting the transport prevents a large embedding set from exceeding OpenSearch's HTTP request limit while preserving exhaustive coverage. Finalization uses one extended-timeout index refresh. Replacing a prior generation deletes concrete stale chunk IDs without refreshing the entire index after every ID, then performs the same single bounded refresh.

Configure ingestion concurrency​

In Settings > Langflow > Knowledge Ingest, use Ingestion concurrency to control how many ordinary files the backend can submit concurrently:

  • Deployment follows MAX_WORKERS and its bounds from Helm or the process environment.
  • Automatic follows the live RQ workers subscribed to Docling's convert queue. The workspace can set its fallback and maximum.
  • Manual uses a fixed number of concurrent ingestion slots.

This setting controls admission inside the OpenRAG backend. It does not change the number of Uvicorn processes, OpenRAG replicas, Langflow workers, or Docling workers. Although the control is grouped with the Knowledge Ingest settings, it is a backend/Docling setting rather than a Langflow graph parameter.

Automatic mode reacts to workers that appear or disappear without restarting OpenRAG. When capacity decreases, active documents continue normally and new documents wait. A temporary metrics failure retains the last valid capacity; after the configured failure threshold, or when no live worker is reported, OpenRAG uses the bounded fallback. Local files at or above OPENRAG_LARGE_INGEST_FILE_BYTES still share one separate serialized heavy lane, regardless of the ordinary-file capacity.

See Environment variables for the metrics URL, refresh interval, minimum, maximum, fallback, and failure threshold.

Configure table parsing​

You can edit the following setting on the OpenRAG Settings page in the Knowledge Ingest section:

  • Table structure: Enables Docling's DocumentConverter tool for parsing tables. Instead of treating tables as plain text, tables are output as structured table data with preserved relationships and metadata. This option is enabled by default.

Configure OCR and image processing​

You can edit the following settings on the OpenRAG Settings page in the Knowledge Ingest section:

  • OCR: Enables Optical Character Recognition (OCR) processing when extracting text from images and ingesting scanned documents. This setting is best suited for processing text-based documents faster with Docling's DocumentConverter. Images are ignored and not processed.

    This option is disabled by default. Enabling OCR can slow ingestion performance.

    If OpenRAG detects that the local machine is running on macOS, OpenRAG uses the ocrmac OCR engine. Other platforms use easyocr.

  • PDF full-page OCR fallback: Checks Docling's first PDF extraction for an empty text layer or a narrow, high-confidence broken character-map signature. When detected, OpenRAG retries that PDF once with full-page OCR and indexes only the second result. If forced OCR still has either problem, ingestion fails instead of storing unverifiable text. Normal PDFs are never retried. This option is disabled by default and is also configurable as knowledge.ocr_mojibake_fallback or OCR_MOJIBAKE_FALLBACK_ENABLED=true before the configuration is edited.

  • Picture descriptions: Adds image descriptions using an explicitly configured remote OpenAI-compatible VLM or a local model installed on every Docling worker. OpenRAG deliberately has no implicit local-model fallback: the switch cannot be enabled until one backend is configured. This prevents an ingestion job from depending on a model that is missing from only some workers. Enabling picture descriptions can slow ingestion performance.

Set the local documents path​

The local documents paths is set when you install OpenRAG and start the OpenRAG services.

The default path for local uploads is ~/.openrag/documents. This is mounted to the /app/openrag-documents/ directory inside the OpenRAG container. Files added to the host or container directory are visible in both locations.

On self-hosted deployments running without user authentication, select Add Knowledge > Ingestion folder to ingest a file or directory already present in this location. Trusted API-key clients that write to the same shared volume can call POST /api/v1/documents/ingest-path; the requested path is restricted to OPENRAG_DOCUMENTS_PATH.

After a file from the ingestion folder is indexed successfully, or its SHA-256 content identifier is already present, OpenRAG removes it from that folder. A matching filename alone is not considered a duplicate. When source archiving is enabled, a newly indexed file is moved instead to OPENRAG_INDEXED_DOCUMENTS_PATH and remains available for preview and download. Failed files remain in the ingestion folder so they can be inspected or retried. Folder ingestion accepts only OpenRAG's verified document extensions. Hidden files such as .DS_Store, partial files, ZIP archives, symlinks, and unsupported formats are skipped before a task is created; they are never submitted to Docling. Local files of at least OPENRAG_LARGE_INGEST_FILE_BYTES use a serialized heavy lane while smaller files can continue to use the remaining Docling worker capacity.

Local path ingestion is disabled in multi-user mode, including through /api/v1/documents/ingest-path. This prevents one user from naming a server-local file that belongs to another user. Use the authenticated multipart POST /api/v1/documents/ingest endpoint instead.

Retain downloadable original files​

Open Settings > Archiving and enable Keep original source files to retain each successfully indexed local upload. OpenRAG moves the original into the displayed archive directory, excludes that directory from later folder ingestion, and stores an authenticated download URL in each indexed chunk's source_url. The workspace setting is persisted across backend restarts and redeployments. Sources that already came from the ingestion folder are restored there if processing fails.

The same setting applies to browser uploads from Add Knowledge. The Archiving page shows the ingestion path, archive path, retained size, filesystem capacity, and free space.

When a knowledge item has a valid source_url, you can download its original from the three-dot menu in the knowledge list, from the Original document section on its chunks page, or from a citation's chunk details in chat. A preview action is also available for PDF, JSON, CSV, Markdown, plain-text, and common image files (AVIF, BMP, GIF, JPEG, PNG, and WebP). The preview opens in a dialog, so you can inspect the source without leaving the current page.

For a PDF citation that includes page metadata, the preview opens on the cited page. Find reference returns the preview to that page; it does not highlight the cited text inside the native PDF viewer. The chunk text remains available in the citation details for comparison.

Local archiving is available only on deployments running without user authentication. In multi-user mode, Settings > Archiving reports that local storage is unavailable and OpenRAG never retains uploaded bytes as a local original. This first implementation deliberately avoids multi-user storage until ownership, tenant isolation, download authorization, and source deletion can be validated with dedicated multi-user tests. Authenticated multipart uploads remain available with or without a source_url.

For an authoritative file hosted elsewhere, API clients can instead submit an absolute HTTP(S) source_url with archive_source=false. OpenRAG keeps the remote URL in search and chat citations without copying the remote file.

To change this location, modify either of the following, and then restart the OpenRAG services:

  • The Documents Paths setting in the Reconfigure terminal option
  • The OPENRAG_DOCUMENTS_PATH variable in the OpenRAG .env file.
