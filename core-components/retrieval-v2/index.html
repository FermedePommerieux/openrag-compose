Retrieval v2

Fork-specific feature

This page documents Retrieval v2 settings implemented by this fork. Names such as Hybrid, Lexical only, and Vector only describe this fork's UI and must not be attributed to official upstream OpenRAG.

Retrieval v2 is the Standard retrieval path for chat, the API, and both SDKs. The backend is the single source of truth for retrieval policy:

Chat → Langflow agent → OpenRAG Retrieval v2 tool → backend /search
     → lexical/vector lanes → RRF → OpenSearch (user-scoped DLS)

The Langflow tool is intentionally thin. It forwards the end-user context and does not implement BM25, KNN, RRF, ACL filtering, reranking, or provenance.

Strategy and configuration​

New installations use RRF by default:

knowledge:
  retrieval_strategy: rrf
  retrieval_mode: hybrid
  retrieval_lexical_candidates: 50
  retrieval_vector_candidates: 50
  retrieval_rrf_k: 60
  retrieval_max_chunks_per_document: 3
  retrieval_scope_seed_count: 100
  retrieval_scope_max_depth: 8
  retrieval_scope_max_entities: 500
  retrieval_scope_max_documents: 250
  retrieval_scope_batch_size: 50

RRF ranks lexical and vector candidates independently and fuses ranks, avoiding comparison of BM25 and vector scores. weighted is retained as an explicit compatibility setting, but is not the Standard baseline. On upgrade, a config without retrieval_strategy resolves to rrf; an explicit persisted weighted value is preserved. Operators may set OPENRAG_RETRIEVAL_STRATEGY to rrf or weighted for a non-edited configuration.

Settings UI​

Administrators with config:write can change retrieval policy in Settings > Retrieval. These settings query the existing index differently and apply immediately; they do not normally require reindexing.

  • Standard (RRF) is the recommended strategy. Existing weighted configurations appear as Legacy weighted retrieval under Advanced / Compatibility and are never converted merely by opening the page.
  • Search mode is available only with Standard (RRF): **Hybrid (lexical
    • semantic)**, Lexical only, or Vector only. Legacy weighted retrieval keeps its compatibility behavior; the stored mode is preserved for a future return to RRF but is not active while weighted is selected. This meaning of Hybrid is unrelated to Docling's Hybrid chunking option in Settings > Langflow > Knowledge Ingest.
  • Lexical candidates and Vector candidates control how many candidates each lane gathers before RRF fusion. RRF k is the fusion constant, not a final top-k. Max chunks per document preserves result diversity.
  • Exhaustive scope investigation exposes explicit safety bounds for broad seed discovery, PROV-O graph depth/entities/documents and verified read batch size. Reaching any bound makes coverage incomplete.

The settings page intentionally does not expose retrieval_reranker_url. The optional reranker endpoint remains backend API/persisted-configuration only until URL validation is hardened against unsafe network destinations. retrieval_debug also remains out of the public UI while its response and logging contract is kept internal.

Equal-score candidates are secondarily sorted by the persisted keyword chunk_id, rather than OpenSearch metadata _id, which is not sortable. New chunks have this field with doc values. Older chunks without it remain searchable and sort last within equal-score ties until re-indexed; they retain best-effort compatibility rather than a claim of complete reproducibility.

chunk_id: keyword with doc values is a hard RRF precondition. OpenRAG reads the live mapping before an RRF request. A missing field, a text mapping, or disabled doc values produces an explicit RRF unavailable error with a reindexing instruction. This does not reject legacy documents that merely lack a chunk_id value: missing: _last keeps those documents searchable.

Identity, authentication, and access control​

The agent forwards the exact end-user JWT as a Bearer token to /search. In OSS mode the same identity resolver accepts either the existing browser auth_token cookie or that Bearer token. The backend then refreshes the user's workspace, owner and DLS principals and creates only a user-scoped OpenSearch client. No service or administrator credential is used for search.

Results preserve document_id, chunk_id, connector_file_id, source_url, filename, page, chunk_index, and chunking_strategy across /search, chat responses, and public v1 streaming SSE citations. Legacy documents may have null or absent provenance fields, but remain readable.

Chat retrieval contract​

The managed Chat agent has only two evidence paths, and both are exhaustive for their declared scope:

  • Every general archive or document search uses scope_exhaustive. Retrieval v2 obtains broad RRF seeds, closes their accessible PROV-O graph forward and backward, then reads every discovered document through the verified pagination primitive. This is the normal path for all grounded questions, not an option reserved for requests containing words such as “all” or “complete”. It needs no confirmation.
  • When the human explicitly selects one already identified document, the agent can perform a complete source-order read of that document.

The managed tool does not expose a focused or ranked-only choice to the model. The deterministic metadata planner follows the same rule: a valid plan without a metadata constraint is routed to scope_exhaustive, never to a bounded ranked-only answer path. Direct API compatibility modes do not change this managed Chat contract.

Graph closure uses the deterministic documentary-prov-o scope policy version 1. PROV-O provenance and documentary scope are deliberately different:

  • email → member_of → email_thread is scope-defining; forward and reverse traversal reconstruct the accessible thread.
  • attachment → attachment_of → email_message, message-compatible reply_to, and RFC 5322 references are also scope-defining for their exact types.
  • email → contained_in → email_archive is contextual, and file → member_of → directory_collection is infrastructure. These links remain visible in compact context/provenance metadata but never open every archive or ingestion-root member.

The policy classifies typed relations before constructing reverse OpenSearch queries. Unknown role/type combinations are not traversed and are not silently certified: they produce scope_policy_unclassified_relation.

Complete source-order reading remains available for one already identified document explicitly selected by the human. The tool then supplies its internal read_document_id, follows the authenticated continuation cursor, and reports coverage under the document's filename. Internal ids and cursors are never human-facing scope labels.

The tool artifact retains full source and PROV-O metadata for source cards. A compact model-facing projection carries chunk text and citation/order fields from ranked seeds, at most one leaf from newly linked documents, and one manifest row per document. This avoids pushing every chunk from hundreds of documents into the model while the complete leaf artifact remains available to the UI. A bounded number of displayed evidence chunks is therefore not a bounded search: the coverage certificate is computed from the complete discovered documentary scope. Generated summaries never replace citable leaf evidence.

Scope coverage is true only when seed discovery succeeds, the graph frontier empties without a guard being reached under the declared policy, no visible relation remains unclassified, and every discovered document completes its immutable-snapshot read. Nested reverse queries keep each relation role, source type, target type and target identifier paired. Every query uses the caller's DLS client. Complete closure describes only accessible indexed entities; it says nothing about documents never ingested or hidden by permissions.

Coverage exposes scope_policy_id, scope_policy_version, and compact relations_traversed, relations_context_only, relations_excluded_by_policy, and relations_unclassified summaries. These are bounded classifications, not a dump of every graph relation.

The machine contract is fail-closed. coverage.status_code is complete only after valid provenance on every seed, natural forward/reverse graph closure, complete contiguous reads of every discovered document, and recomputation of each final document snapshot SHA-256. status_message is human-readable and failure_codes retains every detected cause. Missing/invalid seeds, search or graph errors, safety limits, ambiguous alternate identities, legacy profiles, snapshot changes, invalid cursors, access errors and profile corruption all keep complete=false. Partial verified evidence remains available.

Alternate IDs are identity-only. They can resolve the endpoint of an allowed message relation but do not merge primary source occurrences. Duplicate RFC 5322 occurrences are accepted only with matching message evidence and distinct explicit source containers; unresolved ownership remains identity_ambiguous.

coverage_ratio is retained for compatibility and document_read_coverage_ratio names its exact meaning: document leaf-read progress. Neither ratio certifies graph closure. DLS-invisible targets are excluded from documents, entities and edges and do not consume traversal limits. Reaching a configured bound exactly may still be complete when a visibility probe proves the accessible frontier is naturally empty.

Persisted Langflow flows​

At startup OpenRAG recognizes only the exact locked historical OpenRAG agent graph from lifecycle baseline 156f3664, identified by its expected ID and a versioned canonical graph fingerprint. The comparison normalizes only model and provider credential/endpoint fields that OpenRAG settings are designed to rewrite, and copies those configured fields into the replacement graph. Prompt, code, topology, and every other value remain fingerprinted. It writes a local backup, then uses Langflow 0.11.2's supported PATCH API to unlock the system flow temporarily, replaces it with the bundled OpenRAGBackendRetrievalComponent graph, verifies the persisted wiring, and locks it again. The migration is idempotent. A protected system flow that is missing, altered, partially migrated, or not verified as locked Retrieval v2 fails closed before the backend becomes Ready. An explicitly configured custom flow ID is preserved without automatic migration, settings reapplication, Retrieval v2 guarantees, or prompt synchronization. Startup may still create missing non-chat system flows, but excludes the custom chat flow from creation/recovery and does not run the global flow synchronization that could mutate it. Roll back by restoring the generated backup through Langflow and re-locking the flow.

Hybrid chunking and replacements​

chunking_strategy: hybrid uses Docling's HybridChunker in the backend. Hybrid is fail-fast: unavailable dependencies, unsupported plain text, or a chunking error fail the ingestion task; it never silently falls back to character chunks.

OpenRAG also preserves Docling text regions that HybridChunker intentionally omits as page furniture, such as headers and footers. These supplemental chunks record the page, Docling region label, and spatial position. This keeps identity, legal, navigation, and payment evidence searchable without adding document-type-specific extraction rules.

Replacements are two-phase. OpenRAG first parses, chunks, embeds, and indexes a temporary generation while the old chunks remain available. Only after full success does it promote the new generation and delete the old one. A failed generation is cleaned up without deleting the previous document. Deduplication also includes the requested chunking strategy and relevant parameters, so a character document is not considered unchanged when hybrid is requested.

The replacement scope always includes both the logical document_id and the owner/shared identity. Equal file bytes may be uploaded by different users; reindexing one owner never reads, promotes, deletes, rolls back, or cleans up the other owner's chunks. After a partial delete, restoration checks the global bulk response and every item. An incomplete restore is a fatal error with the affected chunk IDs preserved for recovery.

Query expansion beyond indexed PROV-O relations and a new reranker are not part of this change. Ranked discovery, scope investigation, and selected-document reading remain separate backend-owned contracts.
