Chat in OpenRAG

After you upload documents to your knowledge base, you can use the OpenRAG Chat feature to interact with your knowledge through natural language queries.

The OpenRAG Chat uses an LLM-powered agent to understand your queries, retrieve relevant information from your knowledge base, and generate context-aware responses. The agent can also fetch information from URLs and new documents that you provide during the chat session. To limit the knowledge available to the agent, use filters.

The agent can call specialized Model Context Protocol (MCP) tools to extend its capabilities. The managed retrieval tools remain backend-owned; use OpenRAG Settings for the supported Agent model and prompt changes. Separate custom flows are possible, but do not inherit the managed Retrieval v2 guarantees.

tip

Try chatting, uploading documents, and modifying chat settings in the quickstart.

OpenRAG OpenSearch Agent flow​

When you use the OpenRAG Chat, the OpenRAG OpenSearch Agent flow runs in the background to retrieve relevant information from your knowledge base and generate a response.

If you inspect the managed flow in Langflow, you'll see the components that work together to ingest chat messages, retrieve relevant information from your knowledge base, and then generate responses. The managed flow can be inspected for effective wiring. Supported model and prompt changes are made through OpenRAG Settings and verified through GET /api/settings/runtime-behavior.

  • Chat Input component: This component starts the flow when it receives a chat message. It is connected to the Agent component's Input port. When you use the OpenRAG Chat, your chat messages are passed to the Chat Input component, which then sends them to the Agent component for processing.

  • Agent component: This component orchestrates the entire flow by processing chat messages, searching the knowledge base, and organizing the retrieved information into a cohesive response. The agent's general behavior is defined by the workspace-configured prompt and model that OpenRAG applies to the managed flow. One or more specialized tools can be attached to the Tools port. The managed flow includes MCP Tools and the thin Retrieval v2 tool set, including the bounded metadata-search path when a valid deterministic plan is present. The retrieval path is Chat → Langflow Agent → OpenRAG Retrieval v2 → backend SearchService/RetrievalService → OpenSearch.

    The Agent component selects tools and reasons over their bounded output. It does not decide documentary truth, coverage.complete, strong provenance or DLS.

    How do agents work?

    Agents extend Large Language Models (LLMs) by integrating tools, which are functions that provide additional context and enable autonomous task execution. These integrations make agents more specialized and powerful than standalone LLMs.

    Whereas an LLM might generate acceptable, inert responses to general queries and tasks, an agent can leverage the integrated context and tools to provide more relevant responses and even take action. For example, you might create an agent that can access your company's documentation, repositories, and other resources to help your team with tasks that require knowledge of your specific products, customers, and code.

    Agents use LLMs as a reasoning engine to process input, determine which actions to take to address the query, and then generate a response. The response could be a typical text-based LLM response, or it could involve an action, like editing a file, running a script, or calling an external API.

    In an agentic context, tools are functions that the agent can run to perform tasks or access external resources. A function is wrapped as a Tool object with a common interface that the agent understands. Agents become aware of tools through tool registration, which is when the agent is provided a list of available tools typically at agent initialization. The Tool object's description tells the agent what the tool can do so that it can decide whether the tool is appropriate for a given request.

  • Language Model component: Connected to the Agent component's Language Model port, this component provides the base language model driver for the agent. The agent cannot function without a model because the model is used for general knowledge, reasoning, and generating responses.

    For documentary answers, model knowledge is not source evidence. Claims must remain grounded in the retrieved leaf evidence and its coverage state.

    Different models can change the style and content of the agent's responses, and some models might be better suited for certain tasks than others. If the agent doesn't seem to be handling requests well, try changing the model to see how the responses change. For example, fast models might be good for simple queries, but they might not have the depth of reasoning for complex, multi-faceted queries.

  • MCP Tools component: Connected to the Agent component's Tools port, this component can be used to access any MCP server and the MCP tools provided by that server. In this case, your OpenRAG Langflow instance's Starter Project is the MCP server, and the OpenSearch URL Ingestion flow is the MCP tool. This flow fetches content from URLs, and then stores the content in your OpenRAG OpenSearch knowledge base. By serving this flow as an MCP tool, the agent can selectively call this tool if a URL is detected in the chat input.

  • OpenRAG Retrieval v2 component: Connected to the Agent component's Tools port, this thin tool calls the backend /search endpoint with the end-user identity and active search context. A valid request-scoped metadata plan can instead use the bounded backend metadata-Agent endpoint. The backend, not the flow, owns BM25/vector retrieval, RRF, filters, provenance, coverage and user-scoped OpenSearch DLS. See Retrieval v2 and Structured metadata search.

    Every general document search made by the managed Chat agent is scope-exhaustive. The model has no focused or ranked-only search option. The backend uses ranked retrieval only to discover seeds, closes the accessible documentary graph, verifies the complete reads, and returns a fail-closed coverage certificate. A complete read of one document is used only after the human explicitly selects that document.

  • Chat Output component: Connected to the Agent component's Output port, this component returns the agent's generated response as a chat message.

Nudges​

When you use the OpenRAG Chat, the OpenRAG OpenSearch Nudges flow runs in the background to pull additional context from your knowledge base and chat history.

Nudges appear as prompts in the chat, and they are based on the contents of your OpenRAG OpenSearch knowledge base. Click a nudge to accept it and start a chat based on the nudge.

Like OpenRAG's other built-in flows, you can inspect the flow in Langflow. Treat direct edits to bundled flows as unsupported; create a separate custom flow when you need a custom execution graph. However, this flow is specifically designed to work with the OpenRAG chat and knowledge base. Major changes to this flow might break the nudge functionality or produce irrelevant nudges.

The Nudges flow consists of Embedding model, Language model, OpenSearch, *Input/Output, and other components that browse your knowledge base, identify key themes and possible insights, and then produce prompts based on the findings.

For example, if your knowledge base contains documents about cybersecurity, possible nudges might include Explain zero trust architecture principles or How to identify a social engineering attack.

Upload documents to the chat​

When using the OpenRAG Chat, click Add in the chat input field to upload a file to the current chat session. Files added this way are processed and made available to the agent for the current conversation only. These files aren't stored in the knowledge base permanently.

Inspect tool calls and knowledge​

During the chat, you'll see information about the agent's process. For more detail, you can inspect individual tool calls. This is helpful for troubleshooting because it shows how the agent used particular tools. For example, click Function Call: search_documents (tool_call) to view the call from the thin OpenRAG Retrieval v2 tool to the backend-owned retrieval service. The Langflow flow does not run OpenSearch retrieval itself.

Documentary answers show numbered citation markers in the response and source cards directly below it. Select either one to open the source preview; when the source has a resolvable original, the preview includes a direct document link. Source cards remain visible even if the model omits inline citation markers.

If documents in your knowledge base seem to be missing or interpreted incorrectly, see Troubleshoot document ingestion or similarity search issues.

If tool calls and knowledge appear normal, but the agent's responses seem off-topic or incorrect, consider changing the Agent model or prompt in Settings, as explained in Inspect managed flows and build custom flows.

Change language models, embedding models, and agent instructions​

  1. In OpenRAG, click Settings, and then find the Agent section.

  2. Change the active language model or Agent instructions in OpenRAG Settings. Model changes are persisted in the workspace configuration. To apply new instructions, click Save Agent Instructions. OpenRAG synchronizes these configured values to the managed Langflow flow.

  3. To add a language model, configure its provider on the Settings page, then select the model in the Agent section. The planner follows the Agent model when its own selection is empty; API clients can configure an explicit planner provider/model separately.

    info

    OpenRAG requires at least one language model and one embedding model. If a previously selected provider or model is removed, chat or ingestion can fail until the corresponding runtime selection is changed.

  4. Check GET /api/settings/runtime-behavior after an operational change. MATCH confirms that configured Agent/planner identities and the prompt hash agree with effective execution. Provider credentials are not returned.

  5. For unrestricted Langflow experimentation, create and explicitly configure a separate custom chat flow rather than modifying the managed system flow. A custom flow is preserved, but it does not receive automatic migration, settings reapplication, prompt synchronization or the managed Retrieval v2 guarantees. Export it before upgrades.

  6. After changing supported Agent settings or selecting a custom flow, open Chat and click Start new conversation so the previous conversation does not retain the earlier behavior.

Integrate OpenRAG chat into an application​

You can integrate OpenRAG flows into your applications using the OpenRAG SDKs (recommended) or the Langflow API.

Use the OpenRAG SDKs (Recommended)​

It is strongly recommended that you use the OpenRAG SDKs to interact with OpenRAG programmatically or integrate OpenRAG into an application. This is because OpenRAG passes specific configuration settings to the Langflow API when it runs a flow or conducts a chat session. For more information, see the following:

  • Python SDK README
  • TypeScript/JavaScript SDK README

Use the Langflow API (Not recommended)​

To trigger a flow with the Langflow API, you can get pre-configured code snippets directly from the embedded Langflow visual editor. However, these snippets don't include OpenRAG-specific configuration settings, so the behavior won't be identical to using OpenRAG directly.

The following example demonstrates how to generate and use code snippets for the OpenRAG OpenSearch Agent flow:

  1. Open the OpenRAG OpenSearch Agent flow in the Langflow visual editor:

    1. In OpenRAG, click Settings.
    2. Click Edit in Langflow, and then click Proceed to launch the Langflow visual editor.
    3. If Langflow requests login information, enter the LANGFLOW_SUPERUSER and LANGFLOW_SUPERUSER_PASSWORD from your OpenRAG .env file.

  2. Optional: If you don't want to use the Langflow API key that is generated automatically when you install OpenRAG, you can create a Langflow API key. This key is used to authenticate with the Langflow API; it doesn't grant access to your entire OpenRAG deployment.

  3. In the Langflow visual generate Langflow API code snippets that you can use to run the flow programmatically. For an example, see the Langflow quickstart.
