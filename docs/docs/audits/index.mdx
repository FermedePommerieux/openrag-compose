# Validation

The fork is validated with automated unit, integration, contract and regression
tests. These checks cover retrieval ordering, source citations, access-control
boundaries, metadata filtering, provenance handling and fail-closed coverage
behavior.

Validation also includes reviewed end-to-end scenarios across different
document types and query shapes. Test fixtures, corpus topics, source records,
expected-document lists, captured responses and environment-specific reports
are internal validation data and are intentionally not published in this
documentation.

## Anonymized results

The following aggregate results come from the validation snapshot included
with this fork. Scenario labels are anonymous and no query, document name,
source record or corpus identifier is published.

| Validation | Result |
| --- | --- |
| Deterministic metadata planner | 45 cases; 100% exact parsing, 0% false-positive filter rate, 0% false-negative filter rate |
| Metadata planner latency | 0.044 ms mean, 0.086 ms p95; 0 LLM calls and 0 additional model tokens |
| Retrieval scenario A | 45.8% post-scope document recall, 44.7% component recall, 77.3% precision, 4.384 s mean latency |
| Retrieval scenario B | 60.4% post-scope document recall, 66.7% component recall, 27.2% precision, 4.582 s mean latency |
| Metadata enrichment | 99.43% successful profiles; failures remained fail-closed |
| Automated Python suite at the recorded snapshot | 1,685 tests passed |

Retrieval results use a fixed candidate and scope configuration. They show the
measured trade-off between recall and precision on the reviewed scenarios; they
are not a general performance guarantee. Approximate vector candidate
membership can change with index state even when source text and embeddings are
unchanged.

Public product behavior is defined by the architecture pages and versioned
contracts, not by a particular test corpus or a historical test result.
