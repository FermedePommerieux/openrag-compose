# Retrieval v2

Retrieval v2 is the Standard retrieval path for chat, the API, and both SDKs.
The backend is the single source of truth for retrieval policy:

```text
Chat → Langflow agent → OpenRAG Retrieval v2 tool → backend /search
     → lexical/vector lanes → RRF → OpenSearch (user-scoped DLS)
```

The Langflow tool is intentionally thin. It forwards the end-user context and
does not implement BM25, KNN, RRF, ACL filtering, reranking, or provenance.

## Strategy and configuration

New installations use RRF by default:

```yaml
knowledge:
  retrieval_strategy: rrf
  retrieval_mode: hybrid
  retrieval_lexical_candidates: 50
  retrieval_vector_candidates: 50
  retrieval_rrf_k: 60
  retrieval_max_chunks_per_document: 3
```

RRF ranks lexical and vector candidates independently and fuses ranks, avoiding
comparison of BM25 and vector scores. `weighted` is retained as an explicit
compatibility setting, but is not the Standard baseline. On upgrade, a config
without `retrieval_strategy` resolves to `rrf`; an explicit persisted
`weighted` value is preserved. Operators may set `OPENRAG_RETRIEVAL_STRATEGY`
to `rrf` or `weighted` for a non-edited configuration.

## Settings UI

Administrators with `config:write` can change retrieval policy in
**Settings > Retrieval**. These settings query the existing index differently
and apply immediately; they do not normally require reindexing.

* **Standard (RRF)** is the recommended strategy. Existing `weighted`
  configurations appear as **Legacy weighted retrieval** under Advanced /
  Compatibility and are never converted merely by opening the page.
* **Search mode** is available only with **Standard (RRF)**: **Hybrid (lexical
  + semantic)**, **Lexical only**, or **Vector only**. Legacy `weighted`
  retrieval keeps its compatibility behavior; the stored mode is preserved for
  a future return to RRF but is not active while weighted is selected. This
  meaning of Hybrid is unrelated to Docling's Hybrid chunking option in
  **Settings > Langflow > Knowledge Ingest**.
* **Lexical candidates** and **Vector candidates** control how many candidates
  each lane gathers before RRF fusion. **RRF k** is the fusion constant, not a
  final top-k. **Max chunks per document** preserves result diversity.

The settings page intentionally does not expose `retrieval_reranker_url`.
The optional reranker endpoint remains backend API/persisted-configuration only
until URL validation is hardened against unsafe network destinations.
`retrieval_debug` also remains out of the public UI while its response and
logging contract is kept internal.

Equal-score candidates are secondarily sorted by the persisted keyword
`chunk_id`, rather than OpenSearch metadata `_id`, which is not sortable. New
chunks have this field with doc values. Older chunks without it remain
searchable and sort last within equal-score ties until re-indexed; they retain
best-effort compatibility rather than a claim of complete reproducibility.

`chunk_id: keyword` with doc values is a hard RRF precondition. OpenRAG reads
the live mapping before an RRF request. A missing field, a `text` mapping, or
disabled doc values produces an explicit `RRF unavailable` error with a
reindexing instruction. This does not reject legacy documents that merely lack
a `chunk_id` value: `missing: _last` keeps those documents searchable.

## Identity, authentication, and access control

The agent forwards the exact end-user JWT as a Bearer token to `/search`.
In OSS mode the same identity resolver accepts either the existing browser
`auth_token` cookie or that Bearer token. The backend then refreshes the
user's workspace, owner and DLS principals and creates only a user-scoped
OpenSearch client. No service or administrator credential is used for search.

Results preserve `document_id`, `chunk_id`, `connector_file_id`, `source_url`,
`filename`, `page`, `chunk_index`, and `chunking_strategy` across `/search`,
chat responses, and public v1 streaming SSE citations. Legacy documents may
have null or absent provenance fields, but remain readable.

## Persisted Langflow flows

At startup OpenRAG recognizes only the exact locked historical OpenRAG agent
graph from lifecycle baseline `156f3664`, identified by its expected ID and a
versioned canonical graph fingerprint. It writes a local backup, then uses
Langflow 0.11.2's supported `PATCH` API to unlock the system flow temporarily,
replaces it with the bundled `OpenRAGBackendRetrievalComponent` graph, verifies
the persisted wiring, and locks it again. The migration is idempotent. A
protected system flow that is missing, altered, partially migrated, or not
verified as locked Retrieval v2 fails closed before the backend becomes Ready.
An explicitly configured custom flow ID is preserved without automatic
migration, settings reapplication, Retrieval v2 guarantees, or prompt
synchronization. Startup may still create missing non-chat system flows, but
excludes the custom chat flow from creation/recovery and does not run the
global flow synchronization that could mutate it. Roll back by restoring the
generated backup through Langflow and re-locking the flow.

## Hybrid chunking and replacements

`chunking_strategy: hybrid` uses Docling's `HybridChunker` in the backend.
Hybrid is fail-fast: unavailable dependencies, unsupported plain text, or a
chunking error fail the ingestion task; it never silently falls back to
character chunks.

OpenRAG also preserves Docling text regions that HybridChunker intentionally
omits as page furniture, such as headers and footers. These supplemental chunks
record the page, Docling region label, and spatial position. This keeps identity,
legal, navigation, and payment evidence searchable without adding
document-type-specific extraction rules.

Replacements are two-phase. OpenRAG first parses, chunks, embeds, and indexes
a temporary generation while the old chunks remain available. Only after full
success does it promote the new generation and delete the old one. A failed
generation is cleaned up without deleting the previous document. Deduplication
also includes the requested chunking strategy and relevant parameters, so a
character document is not considered unchanged when hybrid is requested.

The replacement scope always includes both the logical `document_id` and the
owner/shared identity. Equal file bytes may be uploaded by different users;
reindexing one owner never reads, promotes, deletes, rolls back, or cleans up
the other owner's chunks. After a partial delete, restoration checks the global
bulk response and every item. An incomplete restore is a fatal error with the
affected chunk IDs preserved for recovery.

Focused retrieval uses lexical/vector RRF and adaptive per-document diversity.
Exhaustive retrieval reads one verified immutable document snapshot in source
order and returns authenticated continuation cursors plus exact coverage.

When a chat request explicitly asks for exhaustive, complete, all-items,
audit, or verify-everything work, the backend marks that intent in the trusted
Langflow context. A focused discovery call then automatically reads every
exhaustive page for every distinct discovered document before the agent can
answer. This proves the selected
document scope only. Whole-archive thematic completeness requires a future
corpus-snapshot job and is never inferred from ranked discovery.

As of retrieval flow version 11, the component itself follows all continuation
cursors before returning to the agent. This is intentionally not delegated to
the model: a real production replay stopped after 150 of 237 chunks even though
the prompt required completion. A missing or repeated cursor now yields an
explicit incomplete certificate instead of a silent partial answer.

Retrieval flow version 12 separates the two consumers of a tool result. The
LangChain artifact retains every complete chunk record, source URL, ACL field,
ingestion profile and W3C PROV-O object for citation rendering and inspection.
The language-model content receives the same chunk texts and immutable
`chunk_id` values, but document metadata is projected once into a document
manifest and operational fields are omitted. No evidence is ranked away by
this projection. It fixes a measured production case where 237 ordinary chunks
became 512,777 input tokens primarily because the same provenance and profile
were serialized on every row.

This context projection is a transport optimization, not an exhaustiveness
claim. OpenSearch remains responsible for ACL-scoped lexical/vector discovery,
RRF and deterministic source-order reads. A coverage certificate proves only
the scope it names; `focused_discovery_documents` still does not mean the whole
archive. Corpus-wide thematic certification requires an immutable accessible
corpus snapshot plus persisted, batch-level relevance decisions before final
synthesis.

Retrieval flow version 13 gives explicit exhaustive intent a separate
archive-audit discovery profile. The lexical lane opens an immutable
OpenSearch scroll snapshot and consumes it until every matching hit has been
returned; 500 is only its transport page size, never a candidate limit. Scroll
is intentional because the OpenSearch Security plugin rejects PIT creation
when document-level security is active. Each embedding-model lane deepens independently until its
filtered vector population is exhausted, document discovery stabilizes across
successive expansions, or OpenSearch's declared k-NN ceiling is reached. The
response exposes the attempts, reached depth and any truncation instead of
silently treating a budget as truth. A diversity pass then keeps one discovery
hit per document before complete source-order reads begin. Ordinary chat
remains at the administrator-configured candidate depth. The resulting
`archive_audit_candidates` certificate proves that every document in that
multi-lane union was read. Lexical completeness can be certified for the exact
query and PIT snapshot; semantic corpus completeness remains false because a
ranked nearest-neighbour search cannot prove that no unstated synonym exists.

Each embedding model is an independent RRF lane. OpenRAG no longer compares
scores from different vector spaces inside one `dis_max` query: BM25 and every
dense model contribute ranks to the candidate union separately. This permits
measured multi-model ensembles without duplicating OpenSearch clusters. A
three-node OpenSearch cluster can improve availability and throughput, but it
does not by itself change candidate recall, so horizontal scaling must not be
presented as an exhaustiveness feature.

The search context field is a request-scoped Langflow global variable and must
be configured with `load_from_db: true`. Its canonical component name is
`OPENRAG_QUERY_FILTER`, so its exact HTTP alias is
`X-Langflow-Global-Var-OPENRAG_QUERY_FILTER`. Langflow strips the prefix but
preserves the suffix; a hyphenated suffix is a different variable and silently
loses the trusted exhaustive intent. Retrieval flow version 8 migrates the
exact repository-owned version 7 graph to the required `load_from_db` binding.
The shared header-name constant prevents the backend transport from drifting
from the component name.

The field is deliberately a `StrInput`, not a `MultilineInput`. Langflow's
custom-component rebuild path clears `load_from_db` after assigning a
multiline value, which would downgrade every request back to focused retrieval
after startup. Retrieval flow version 9 migrates both exact repository-owned
version 8 states (before and after that normalization) to the stable string
binding; edited graphs still fail closed.

On clustered deployments, `OPENRAG_FLOWS_PATH` may point to a shared volume
rather than the files baked into the backend image. The GitOps flow revision
must therefore equal the immutable source revision behind the image tag, and
the deployment refreshes those shared files on rollout. Retrieval flow version
10 safely repairs the exact stale-volume v9 state that exposed this mismatch.

The Knowledge document-detail page uses the same exhaustive contract. The
table passes the stable `document_id`; legacy filename-only links first resolve
that identity through an exact `data_sources` lookup. The frontend then follows
every authenticated cursor before displaying chunks. It never derives a
document detail from a bounded corpus-wide `*` result set. The Original
document panel also renders the stored `source_provenance` JSON so entity and
relation metadata remain directly inspectable.

Inspectors may switch from source order to relevance after entering a query.
This performs a second hybrid search scoped to the exact open filename and
merges its scores into the already complete chunk set. Scored candidates appear
first; unscored chunks remain visible afterward. Relevance therefore changes
presentation only and never becomes a coverage filter.
