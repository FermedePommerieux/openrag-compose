# Retrieval v2

Retrieval v2 is the standard search path for chat, the API, and both SDKs. The
backend is the single source of truth for retrieval policy:

```text
Chat → Langflow tool → backend /search
     → lexical + vector lanes → RRF + normalized score → consensus → direct plane
     → OpenSearch-native PROV-O predicate matching
     → backend fixed-point orchestration → context plane + document graph
```

The Langflow component only forwards the authenticated request and projects the
response for the model. It contains no OpenSearch query, graph traversal,
ranking, ACL, or validation policy.

## One normal search path

There is no separate thematic "exhaustive" or "audit" search mode. Every
focused query uses the same complete accessible knowledge index and the same
PROV-O relation machinery. `exhaustive` remains an API operation for reading
all chunks of one explicitly selected `document_id` in source order; it is not
an archive-wide reasoning workflow.

The normal path has two deliberately separate planes:

1. **Direct plane.** BM25 and each available embedding model produce ranked
   candidates. The backend computes both RRF and an equal-weight arithmetic
   mean after min-max normalization inside each lane. A final RRF converges
   those two rankings without comparing their incompatible score magnitudes.
   The configured result limit applies to this plane.
2. **Context plane.** Direct documents seed OpenSearch `nested` queries over
   full `source_provenance.relations.prov_predicate` URIs and paired target
   identities. The backend submits each new frontier until a fixed point is
   reached inside the caller-visible graph. One representative chunk for each
   newly related document is appended after the direct plane.

`contained_in` is intentionally ignored: documents sharing a mailbox or an
archive are not necessarily about the same subject.

## Relevance and intentional noise

PROV-O context is useful precisely because a reply can say "your project"
without repeating the project's name. It can also introduce documents that are
related but not responsive. Retrieval v2 preserves that ambiguity instead of
hiding it behind an LLM decision.

Each returned document receives an explainable class:

| Class | Meaning |
| --- | --- |
| `strong` | Direct lexical match, optionally corroborated by the semantic lane |
| `exploratory` | Direct semantic-only match |
| `contextual` | Relation-only document reached in one PROV-O graph expansion step |
| `peripheral` | Relation-only document reached after multiple graph expansion steps |

These are discovery-strength classes, not probabilities and not truth
verdicts. No LLM excludes, validates, or labels documents. The response exposes
`retrieval_planes`, `noise_accounting`, and `document_graph` so the chat and the
human can distinguish direct evidence from intentionally retained context.

Relation-only documents never enter the direct RRF list and cannot displace a
direct result. They are ordered by graph traversal distance and OpenSearch rank
within each frontier. The source artifact retains every returned document;
the model-facing projection shortens context-only excerpts to control tokens.

## Document graph contract

`document_graph` is generated deterministically from persisted `source_provenance`
relations and the observable paths returned by the fixed-point traversal. It
contains:

- one node per returned document;
- the representative `chunk_id`, filename, direct/context plane, relevance
  class, graph component and relation count;
- asserted edges with source document, target document, canonical PROV-O
  predicate URI, OpenRAG role qualification, direction, edge kind, and entity
  id;
- shared-target projections represented explicitly as two persisted assertions,
  never as an invented PROV-O predicate between the documents;
- connected components and exact node/edge counts;
- `llm_generated=false`.

A model cannot invent an edge. If provenance is absent on a legacy document,
that document remains searchable through lexical/vector retrieval but has no
graph claim.

OpenSearch owns predicate/target matching, filtering, DLS enforcement, sorting,
and exhaustive scrolling of each frontier. The backend owns recursion only;
OpenSearch is not presented as an RDF reasoner. The response exposes the
canonical field, traversed predicates, role exclusion policy, legacy fallback,
iteration counts, `frontier_stabilized`, and `fixpoint_reached`. The latter is
true only when the frontier stabilized **and** every OpenSearch scroll was
exhausted.

## Strategy and configuration

New installations use consensus fusion and Hybrid retrieval. The persisted
`rrf` value is retained for configuration compatibility; its effective
Standard behavior is RRF plus normalized-score consensus:

```yaml
knowledge:
  retrieval_strategy: rrf
  retrieval_mode: hybrid
  retrieval_lexical_candidates: 50
  retrieval_vector_candidates: 50
  retrieval_rrf_k: 60
  retrieval_max_chunks_per_document: 3
```

Administrators can change these settings under **Settings > Retrieval**.
Candidate counts bound the direct ranked lanes, not the PROV-O component. The
context plane is complete for the disclosed predicate/role policy and
accessible connected component when `fixpoint_reached=true` and every
OpenSearch scroll is exhausted.
This does not prove that semantic search found every possible paraphrase.

The two first-stage rankings reuse the exact same materialized OpenSearch lane
responses. No replica, second index, additional OpenSearch request or language
model call is required. RRF contributes rank agreement; lane-local min-max
normalization preserves meaningful score gaps without allowing BM25 magnitude
to dominate vector similarity. The response exposes `retrieval_fusion`,
including the effective strategy, normalization rule, final fusion constant,
and the explicit `additional_opensearch_requests: 0` and `llm_used: false`
contracts.

This ensemble improves ordering robustness but does not create candidates that
are absent from every direct lane. Recall comes from complementary BM25,
embedding-model and PROV-O discovery; fusion decides how their direct
candidates are ordered.

Equal-score candidates are secondarily sorted by persisted keyword `chunk_id`.
`chunk_id: keyword` with doc values is a hard RRF precondition. Older documents
without a value remain searchable and sort last; an incompatible mapping fails
with an explicit reindexing instruction.

## Authentication and sources

The agent forwards the exact end-user JWT to `/search`. The backend refreshes
the caller's workspace, owner, and DLS principals and creates only a user-
scoped OpenSearch client. Graph traversal uses the same client and filters, so a
relation can never cross the caller's access boundary.

Results preserve `document_id`, `chunk_id`, `source_url`, `connector_file_id`,
filename, page, ingestion profile, flattened provenance identities, relation
paths, graph distance and relevance class. The chat tool artifact keeps the
full source records for citation and preview. Model content receives compact
document metadata and shorter context-only excerpts.

## Single-document complete reading

`evidence_mode=exhaustive` reads one immutable document snapshot in source
order. The continuation cursor is bound to the document digest and access
scope. `coverage.complete=true` proves only that named document snapshot was
read; it says nothing about archive-wide thematic completeness.

This operation supports document inspection after a human selects a result. It
is never launched automatically across all search candidates.

## Hybrid chunking and replacements

Retrieval Hybrid mode is unrelated to Docling Hybrid chunking. Hybrid chunking
uses Docling's `HybridChunker` and fails fast rather than silently falling back
to character chunks. Supplemental page-furniture chunks preserve headers,
footers, legal identity, navigation and payment evidence that Docling may omit.

Replacements are two-phase. OpenRAG parses, chunks, embeds and indexes a
temporary generation while the old one remains available. It promotes the new
generation and deletes the old only after complete success. Replacement scope
includes both logical `document_id` and owner/shared identity.

## Langflow flow ownership

The repository-owned flow is migrated only when its complete canonical graph
matches a known OpenRAG fingerprint. Customized Langflow graphs fail closed and
are never overwritten. Flow version 18 moves PROV-O into every normal query,
removes the automatic archive-read cascade, exposes direct/context retrieval
planes, and gives the source panel a clear visual distinction between direct
matches and intentional relation context.
